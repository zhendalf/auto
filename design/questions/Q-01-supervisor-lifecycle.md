# Q-01 — How should the supervisor process stay alive?

## Context

The supervisor is a long-running Bun process that owns:
- The cron scheduler (replacing direct `Bun.cron` registration)
- An HTTP server (webhook receiver + JSON API + static SPA)
- File watchers
- Run history / SQLite writes

This is the foundational architectural decision — everything downstream
(socket vs HTTP for CLI, log paths, restart semantics, fresh-machine
bootstrap) depends on how the process is kept alive.

## Options

### a) macOS LaunchAgent (`~/Library/LaunchAgents/`)

`RunAtLoad=true`, `KeepAlive=true`. Started automatically at login,
restarted on crash, dies when the user logs out.

- Pros: native to macOS, no extra deps; logs go to file paths we choose;
  re-installable via a `bun install-launchagent.ts` script.
- Cons: doesn't run when logged out (fine for a personal laptop, not
  fine for jobs that must run while user is logged out).

### b) macOS LaunchDaemon (`/Library/LaunchDaemons/`)

Same mechanism but runs as root, even when no user is logged in.

- Pros: runs while logged out.
- Cons: root, system-level plist, security footgun for personal repo.

### c) Manual `bun supervisor.ts` in tmux/cmux

User starts it by hand.

- Pros: simplest possible.
- Cons: dies on reboot; user has to remember to start it.

### d) Third-party supervisor (`pm2`, `forever`, Bun's own runner)

- Pros: cross-platform.
- Cons: extra dependency for a problem launchd already solves on macOS.

## Recommendation

**(a) LaunchAgent.**

- Native, no extra deps.
- `RunAtLoad=true` + `KeepAlive=true` covers reboot survival and
  crash restart.
- Plist generated by a script in the repo, so fresh-machine setup is
  one command.
- The bun-autoupdate worker can migrate from `Bun.cron` to
  "supervisor invokes the worker on schedule" without changing the
  worker file (still exports `default { scheduled() }`).

## Tradeoff to flag

LaunchAgents only run when the user is logged in. If a future job
needs to run while logged out (e.g., 4am backup on a shared laptop),
a LaunchDaemon would be required — different security posture (root,
system plist).

## Question for reviewer

Is **(a)** the right call? Are there reasons to prefer (c) early
(simpler bootstrapping while the system is being designed) and only
move to (a) once the supervisor is stable? Anything missed?

## Codex verdict

**Verdict:** AGREE-WITH-CAVEAT

**Reasoning:**
- LaunchAgent is the right production default for this repo: single-user macOS laptop, user-owned files, notifications, Homebrew/Bun paths, and no root boundary. LaunchDaemon is disproportionate risk.
- Do not use `(c)` as the architecture choice. Keep a foreground `bun supervisor.ts` mode for development/debugging, but design install/restart/log/state semantics around LaunchAgent from the start.
- The current worker shape already fits this migration well: workers can remain directly runnable and export `scheduled()`, while the supervisor becomes the caller instead of Bun.cron.
- `KeepAlive=true` is only correct if the supervisor is genuinely long-running. If it exits cleanly after setup or on config error, launchd will repeatedly restart it unless you define failure behavior carefully.

**Anything missed:**
- LaunchAgent environment is sparse. The plist should set `WorkingDirectory`, absolute Bun path, explicit `PATH`, `StandardOutPath`, `StandardErrorPath`, and probably `ThrottleInterval`.
- Decide restart semantics for bad config/database migration failures. Infinite crash loops can corrupt logs and hide the real issue.
- Webhooks on a laptop need a clear network story: localhost-only, Tailscale-only, reverse tunnel, auth token, or no external exposure.

**Recommended choice:** a) macOS LaunchAgent, with a required foreground/manual mode for development and recovery.
